# 云端与本地服务器更新并存

发布页面继续用 github/local 构建选择。云端生成 GHCR 版本镜像；本地生成原生 Web ZIP 并发布 GitHub Release。本地交付配置声明 `deployment.strategy=server-pull`，RunDock 只观察线上版本，不调用 Actions。已有 workflow 部署契约仍可用于其它项目和历史批次。

NAS 独立更新服务是本应用唯一的部署执行者，每 300 秒查 GitHub 上最高稳定 Web Release。存在原生 manifest 时下载并验证 ZIP、按冻结提交补充 Docker 运行配方和下载同步脚本，在 NAS 装配镜像；否则拉取该版本 GHCR 镜像。两条路径统一使用 Compose、数据库备份、持久部署日志、单进程锁及线上版本核验。原 Watchtower 仅对本服务退出执行，避免覆盖本地镜像；其它服务不在范围内。

凭据复用 NAS 现有读取权限，保存在 0600 文件，只读挂载给没有公网端口的更新服务。Docker socket 是部署授权边界；部署服务只能接收固定仓库/Compose 服务配置，不开放远程执行 API。外部 Release、ZIP 和元数据均需限额、路径与身份校验。数据卷和原始私有 Compose 保留。

实现前列出的失败方式及端到端验收：

- 私有仓库认证/限流/分页不完整：明确失败并保留当前服务，不能把未找到当成云发布。
- ZIP/manifest/Tag/提交/镜像标签不一致、重复路径或穿越：阻止更新；损坏原生成品不能降级走云端。
- 本地与云端交错、旧版本稍后完成、重复定时器：只处理最高稳定版本，同一锁内重新核对；不同提交不能重用同版本。
- 下载/装配失败：当前容器继续运行，重试有界且跨轮退避。
- 镜像完成但新服务无法启动/版本不匹配：回到原镜像；数据迁移不可盲目还原，记录人工处理原因。
- 服务重启发生在替换中：持久保存旧镜像和候选身份，先核验/恢复再处理新 Release。
- 首次安装识别现有版本，不重复部署；验收允许在同一版本同一提交上切换两种路径，禁止借验收创建新版本。
- 更新包不能丢失 PC/Android 下载脚本；线上静态文件/版本/下载接口必须再次确认。

验收采用最后阶段的定向端到端脚本：真实 HTTP Release 边界、真实进程重启与持久文件、Docker/Compose 边界故障注入；NAS 使用已上线 2.0.43 做本地与云端两条实际部署路径验证，无新应用版本、无全套功能测试。本次工作可通过恢复 Compose 覆盖文件、停止独立更新服务和恢复原 Watchtower 设置撤回。
