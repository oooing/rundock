# 发布文件保留规则

RunDock 默认启用旧安装包清理，无需设置。维护在后端启动时及每 5 分钟运行一次。

- 仅清理已经完整发布到 GitHub 的成功记录：同一项目、仓库、发布组、平台组合和正式/预发布通道保留最近 3 次成功发布的本地副本；其他副本也至少保留 30 天（从发布完成时计算）。两个条件必须同时满足。
- 失败待重试、取消、排队、运行中、上传未完成，以及服务器同步未确认的记录不自动清理。
- 仅本地生成的文件是用户的原始交付结果，不自动清理。
- 清理只删除 RunDock 封存目录中清单列出的安装包副本，不碰项目源码、原目录中的安装包、构建缓存、GitHub 文件或其他未知文件。
- 发布记录、文件名、大小、校验值、清单和 GitHub 下载链接仍保留。历史详情显示“本地副本已清理”，历史大小不是当前磁盘占用。

维护会避开正在检查、构建或发布的仓库，并校验目录和清单。遇到路径替换、符号链接、清单不一致或文件占用时不强行删除。清理中断后保留清理状态，下次维护继续；不会为清理触发重新构建、上传或登录。

这些规则不是整个缓存目录的空间上限。失败记录、本地生成结果、构建缓存以及不符合清理条件的旧文件仍可能占用空间。

## GitHub 连接失败后继续

“登录检查”本身也需要联网。超时、连接中断、代理失败不再被当作登录失效。账号检查与 API 请求使用相同的代理处理；只读网络检查最多自动重试一次，上传和发布写操作不会盲目重复。

在网络恢复后，打开项目的“发布历史”，选择失败记录，再点击“重试上传”。系统先核对已保存文件及远端状态，再继续未完成步骤。无需重新生成，也不会仅因网络超时要求退出或重新登录。只有明确未登录或凭证被拒绝时才提示登录。
