# 多服务项目的启动与停止约定

普通项目仍然导入启动脚本即可，不要求额外配置文件。

当项目包含多个必须一起工作的服务时，可在 `.cmd` / `.bat` 入口顶部加入可选注释：

```bat
rem rundock:open http://127.0.0.1:4310/library
rem rundock:ready http://127.0.0.1:4310/library
rem rundock:ready http://127.0.0.1:4311/api/health
```

PowerShell `.ps1` 使用同样的内容，把 `rem` 换成 `#`。`.cmd` 也支持 `::` 注释。

- `rundock:open` 可选，指定“打开项目”的主页面，只能声明一次，可保留路径和查询参数。它不自动成为就绪要求；`ready` 可在相同端口另行声明。
- 未声明主地址时，优先选择当前运行的健康前端，其次已识别前端，再沿用最近地址或当前服务地址。直接点击某个服务链接时仍打开该服务。
- 地址必须为带明确端口的本机 HTTP/HTTPS 地址；`ready` 每行一个，每个端口最多声明一次。
- RunDock 只检查本次运行已发现归属的服务，其他进程占用同端口不会算作本项目就绪。
- 每个明确地址均须返回 2xx/3xx；不会用另一个健康路径或首页的 200 替代该地址的失败。
- 所有必要服务首次就绪前显示“启动中”，不因启动耗时超过固定秒数而标为“降级”或提示“启动较慢”。就绪后显示“运行中”；真实的进程退出、停止和后续健康异常仍按原有机制处理。
- 旧脚本的 `rundock:timeout` 声明仍兼容读取和格式校验（1–600 秒），但不再限制启动等待；旧的服务发现超时设置也不再参与启动状态判定。设置页不再提供此项。
- 没有 `rundock:ready` 时保持原有自动发现方式，端口提示和角色日志不会自动成为强制要求。
- 无效声明在启动前报错，不悄悄忽略。健康后仍持续监测，沿用连续失败确认和恢复机制。
- 有 `rundock:ready` 声明时，仅声明的必要服务影响项目运行状态；自动发现的其他端口显示为“辅助”，不会因辅助端口不可达而降级。没有声明时，沿用自动发现服务的整体健康判定。自动发现的无声明端口须有成功的页面或健康响应，HTTP 400/404 等错误本身不作为服务证据；日志、端口提示和明确角色声明仍可识别健康尚未通过的服务。
- 必要服务连续健康检查失败时，卡片直接列出失败端口、具体原因（例如 HTTP 503、超时、连接被拒绝）和检查地址；恢复后提示随状态自动消失。辅助端口仍可查看，但不混入降级原因。

针对性验证：`go test ./internal/launcher ./internal/probe ./internal/store ./internal/api -count=1`（在 `sidecar` 下运行）；前端构建后运行 `node scripts/acceptance/service-health-ui.mjs`。浏览器验收仅使用模拟 API，覆盖辅助端口、具体失败原因、恢复、多语言与窄屏显示，不启动、停止或重启真实项目。

启动入口应保持前台运行，失败返回非零退出码，避免 `pause`、脱离托管进程树和交互式安装依赖。

BrickMuse 的实际入口使用 `call npm run dev <nul`。该项目不需要终端输入，`<nul` 用于避免 Ctrl+C 后批处理等待终端确认；不要给需要键盘输入的其他项目统一加这个重定向。

停止时先发送 Ctrl+C，保留超时强制终止的兜底。强制终止在有效的根进程和终端句柄仍存在时进行，随后回收资源。RunDock 等待根进程以及本次停止时跟踪的子进程退出；若未完成则报错并保留可重试状态，不宣称已停止，也不按端口号杀陌生进程。

界面从同一份当前运行视图读取状态、PID、主地址和服务列表。停止或失败后不再把历史端口显示为健康服务；重启后切换到新 PID，晚到的旧运行消息不会恢复旧服务。WebSocket 重连也会重新读取运行信息。

本轮没有增加部署流程，发布扫描仍是后续事项。

回归命令：在 `sidecar` 目录运行 `go test ./internal/launcher ./internal/proc ./internal/probe ./internal/api -count=1`；在代码根目录运行 `node --test scripts/tests/apps-store.test.mjs` 和 `npm run type-check`。

## 重启与外部运行项目

- 已托管项目保留「停止 / 重启」主按钮，继续使用正常停止与启动流程。
- 外部运行项目保留「重启」主按钮；点击只核验进程归属并显示确认窗口，不会直接关闭。只有唯一、完整的启动进程树可以确认：入口脚本、原生进程创建时间、可执行文件、用户会话及父子关系均需核对。确认在 60 秒后过期、单次使用、绑定项目和页面来源；确认后再次核验。身份变化、共享浏览器/编辑器子进程、独立服务、其他托管项目或系统程序一律不猜测关闭。
- 外部重启会结束已确认的进程，可能丢失未保存内容。它不伪装成已持有原项目的终端会话，也不通过进程名、端口号或 `taskkill /T` 猜测进程树；全部原生句柄核验通过后才开始关闭，启动前再次检查端口和配置。
- 运行状态由后台自动更新，不提供「刷新运行状态 / 重试检测」作为修复操作。无法核实归属、权限不足或有任务阻止重启时，直接说明原因，不显示通用重试按钮；启动失败保留原因、日志和实际的启停操作。端口处理窗口仅在确认可安全关闭时提供「关闭并启动」，否则只展示阻止原因。
- 仅有效操作的确认信息过期时提供「更新确认信息」，更新后仍需用户再次确认才执行；它不处理权限、配置或归属问题。执行失败后保留具体错误，不自动重试或沿用已消费的确认令牌。
- 构建、发布、候选检查的执行预约与重启互斥；任务进行中明确提示等待，不自动取消任务。RunDock 自身重启前还要求没有活跃的托管项目，防止关闭其进程句柄。
- RunDock 自重启交给独立启动器：开发环境的 `scripts/dev.ps1` 保持前端运行，后台明确以 75 退出时重新编译并启动；桌面壳以 `--supervise` 启动后台，独立监督进程只对明确的重启请求重新拉起，不对普通崩溃无限重试。前端以变化的 `instanceId` 和健康响应确认完成，最长等待 90 秒，未确认时显示错误且不再次重启。
- 旧进程无法热更新自己的启动器。升级这项能力后，需要从新版启动器重新打开一次；旧启动器下明确说明此原因，绝不先结束后台再碰运气拉起。

针对性验证：`node --test scripts/tests/restart.test.mjs`；`node scripts/acceptance/restart-ui.mjs`（可用 `RUNDOCK_PLAYWRIGHT_MODULE` 指定 Playwright 模块）；`go test ./internal/api ./internal/recovery ./internal/publisher ./cmd/launcher-sidecar -run 'Test(Restart|ManagedRestart|SelfRestart|Supervisor)' -count=1`。浏览器验收拦截全部 API，仅使用模拟数据，不重启真实用户项目。
