# 本地 Web 成品发布与服务器更新

状态：保留为首次部署的历史决策。LocalPlay 本地交付现改为 NAS 拉取更新，不再使用 GitHub 打包；以 [双模式服务器更新](2026-10-04-dual-server-update.md) 为准。通用的显式工作流部署契约继续保留给需要此方式的项目。

## 目标和职责

本地构建生成已校验的 Web ZIP；RunDock 发布封存的 GitHub Release 后，按该批次冻结的 `delivery.deployment` 显式调用部署工作流。GitHub 从指定 Release 取回前端成品，从同一个不可变提交取回 Python 后端，在 Linux 打包 Docker 镜像，推送 GHCR；NAS 原有 Watchtower 拉取镜像并更新容器。版本接口核验是完成条件，Release 存在或镜像上传都不是线上升级完成。

部署配置是项目选择，未配置的旧发布保持原语义。产物上传、镜像工作流、线上同步各自有独立结果；失败可查询原任务并重试，不能因为部署失败覆盖已公开产物，也不重复编译 PC/Android。

## 实现前列出的失败方式

- Release、Tag、提交、ZIP 摘要或包内身份不同：拒绝镜像打包。
- 工作流未同步、账号不符或发布尚未公开：不触发部署。
- 请求返回丢失或服务重启：持久记录提交时间，优先查询同一批次的工作流；不盲目重复触发。
- 旧版本任务晚于新版本完成：发布前比较当前主 Web 版本，阻止旧版本覆盖 latest。
- 工作流失败：保留 GitHub 链接和明确错误，不把 Release 标记为未上传。
- 镜像成功但 NAS 未更新、离线或版本不同：保持待同步，不能声称部署完成。
- 更新影响持久数据或同步脚本：保留现有 Compose/数据卷，更新前保存数据库及原镜像摘要；检查 PC/Android 下载接口。
- ZIP 路径穿越、软链接、超大内容、敏感文件：使用有界提取和白名单；凭据只供 GitHub 原有登录步骤使用。
