# RunDock 界面文案规范

## 写给使用者，不写给实现者

名称用 2–6 字说清对象或动作；说明最多 40 字。已经清楚的“启动”“停止”“重启”“保存”“取消”保留，不为改而改。

这里的字数约束针对中文固定文案和说明模板。用户的项目名、路径、版本号、命令和原始运行记录保留完整，不硬截断；英文按自然表达翻译，不机械限制为 6 个字母。

## 统一叫法

| 原说法 | 新说法 | 使用场景 |
| --- | --- | --- |
| 全部应用 | 全部项目 | 导航、页面标题 |
| 入口脚本 | 启动文件 | 添加项目、项目卡片 |
| 降级 | 部分异常 | 项目状态 |
| 查看日志 | 查看记录 | 项目卡片 |
| 打开 URL | 打开页面 | 项目卡片 |
| 配置导入导出 | 备份与恢复 | 设置 |
| 本地构建并发布 | 本机发布 | 本机生成后上传 GitHub |
| 云端构建并发布 | 云端发布 | GitHub 生成并发布 |
| 仅本地打包 | 仅本机打包 | 不在线发布 |
| 产物 | 生成文件 | 发布结果、下载列表 |
| 仅提交代码 | 保存代码 | 保存一条代码记录，不等于上传 |
| 留在本地 | 本次跳过 | 只跳过这次改动，不等于永久忽略 |
| 敏感阻断 | 含私密信息 | 文件安全检查 |

## 四条写法

1. **动作明确**：按钮说“做什么”，不让用户猜“处理”“确定”的后果。删除、停止其他程序、上传等风险紧邻按钮说明。
2. **称呼一致**：同一对象统一叫“项目”；同一动作在按钮、提示和帮助中用相同名称。
3. **主次分明**：名称短，条件与后果放在旁边的说明里；高级检查的字段名和填写说明分开。
4. **结果可信**：生成完成、上传完成、正式发布、服务器更新分别说明；未知不写成成功，重试不承诺修复。

说明示例：

- 本机发布：本机生成，上传到 GitHub 发布。
- 临时换端口：只改这次端口，不停其他程序。原设置保留，下次普通启动仍用原端口。
- 跳过文件：只跳过这次修改，下次仍可能询问。
- 部分异常：项目仍在运行，但部分服务暂不可用。恢复后会自动更新状态。

## 覆盖与维护

覆盖导航、项目卡片、添加项目、设置、动画、帮助、关闭与重启、端口占用、更新、发布选项、文件检查、生成与上传进度、结果和错误提示。

显示文案集中在 `src/i18n/productCopy.ts`。原来的翻译键保持稳定，避免文案修改影响 API 消息匹配或操作逻辑。中文、英文成对维护；未知错误和用户输入不会被关键词批量替换。

`npm run test:i18n` 会验证：名称与说明长度、中英覆盖、插值参数、未知文本原样保留、系统语言和手动语言选择优先级。更改文案后还应运行 `npm run build` 并检查实际界面。

本次只修改显示层，不重启后台、不停止项目，也不发起真实发布。已安装的桌面版需使用包含这些修改的新安装包。

## 原则来源

- [Steve Krug：Don't Make Me Think](https://sensible.com/dont-make-me-think/)：减少用户理解界面所需的思考，采用熟悉、明确的表达。
- [Robin Williams：The Non-Designer’s Design Book](https://www.peachpit.com/store/non-designers-design-book-9780321193858)：借用亲密性、对齐、重复和对比的原则，把名称、说明与操作组织清楚。本次不重做布局。
